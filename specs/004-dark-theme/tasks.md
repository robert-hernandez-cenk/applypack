**Purpose**: the second token set and its emission. Every story depends on it.

- [ ] T002 Write failing tests in `src/web/tokens.test.ts`: (a) `LIGHT_TOKENS` and `DARK_TOKENS` have identical key sets; (b) the existing text-on-surface AA matrix (`ink`, `ink-muted`, `ink-faint` at 5:1, `accent-strong` at 4.5:1 on all four surfaces, the row hover, and each status tone) runs over both sets, with the pill tint blended over the active set's `surface-raised` instead of the fixed `WHITE`; (c) `rootBlock()` emits `:root {…}` (light), `:root[data-theme="dark"] {…}` and `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {…} }`, each with `color-scheme`.
- [ ] T003 Implement in `src/web/tokens.ts`: export `LIGHT_TOKENS` (the current `TOKENS`, keep `TOKENS` as an alias used by the rest of the code) and `DARK_TOKENS` `satisfies Record<TokenName, Rgb>`; add the non-colour tokens the plan needs (`shadow-ink`, `scrim`) to both; rewrite `rootBlock()` to emit the three rules. Choose dark values until T002 passes (canvas near-black, raised surfaces one step lighter, off-white ink, lifted accent and status tones). Existing callers of `rootBlock()` keep working.

**Checkpoint**: `npm run lint:types && npm test` green; light pages unchanged.

## Phase 4: User Story 2 - Choose System / Light / Dark (P1)

**Goal**: a three-way switch whose choice sticks per browser and is applied server-side on first paint.

**Independent Test**: choose Dark with a light OS → dark across pages and after restart; choose System → follows the OS.

- [ ] T009 [P] [US2] Write failing `src/web/theme.test.ts`: `parseTheme` is total (`'light'`/`'dark'` map to themselves; `undefined`, `''`, `'DARK'`, `'blue'` → `'system'`); `themeAttr('system')` is `undefined`, `themeAttr('dark')` is `'dark'`; `withTheme`/`currentTheme` round-trip and `currentTheme()` is `'system'` outside a request.
- [ ] T010 [US2] Implement `src/web/theme.ts` (named exports: `THEMES`, `Theme`, `THEME_COOKIE = 'theme'`, `THEME_COOKIE_MAX_AGE`, `parseTheme`, `themeAttr`, `withTheme`, `currentTheme`), modelled on `src/web/language.ts`. Data model: value is `'system' | 'light' | 'dark'`; `system` is stored as no cookie.
- [ ] T011 [US2] In `src/web/app.ts`, extend the `'*'` middleware to read the `theme` cookie with `getCookie` (`hono/cookie`) and wrap `next()` in `withTheme(parseTheme(raw), …)`, inside the existing `withLocale`/`withLanguagePage` nesting.
- [ ] T012 [US2] In `src/web/layout.tsx` render `<html lang=… data-theme={themeAttr(currentTheme())}>`; do the same in the sign-in document in `src/web/oidc/pages.ts`.
- [ ] T013 [US2] Add `POST /settings/theme` to `src/web/routes/settings.tsx` per `contracts/theme-route.md`: parse `theme` and `back`, `safeBack(form.back, '/')`; `light`/`dark` → `setCookie(THEME_COOKIE, value, { path: '/', maxAge: THEME_COOKIE_MAX_AGE, sameSite: 'Lax', httpOnly: true, secure: c.req.url.startsWith('https:') })`; `system` → `deleteCookie`; unknown → no change; 303 to back. No flash message.
- [ ] T014 [P] [US2] Add the `theme.*` keys (label, system, light, dark, trigger/aria text, Settings row title and hint) to all four catalogs `src/i18n/catalog/{en,es,fr,uk}.json`, then `npm run i18n:browser` if `catalog.test.ts` or the browser mirror requires it.
- [ ] T015 [US2] Create `src/web/theme-switch.tsx`: a segmented control (three submit buttons `name="theme"`, sun/moon/monitor icons via `src/web/icons.tsx`, `aria-current` on the active one, hidden `back` input from `languagePage().back`), `data-ui` hooks per CLAUDE.md for helper prose; mount it in the sidebar foot next to `LanguageMenu` in `src/web/layout.tsx` and as a row under Settings → General in `src/web/pages/settings.tsx`. Respect the icon-rail widths used by `language-menu.tsx` (`md:` / `lg:` classes).
- [ ] T016 [US2] Extend `src/scripts/route-smoke.ts` (and its fixtures if needed): same-origin `POST /settings/theme` with `theme=dark` sets the cookie and 303s back; `theme=system` clears it; a cross-origin POST is refused; the page with the cookie carries `data-theme="dark"`.
- [ ] T017 [US2] Add the row "theme / appearance" to `docs/where-to-look.md`.
- [ ] T018 [US2] Run `npm run css`, `npm run lint:types && npm test`; verify T016 locally on a throwaway DB (`npm run build && npm run smoke:routes`); commit "theme switch with cookie (#4, US2)"; push.

## Dependencies & order

- Phase 1 → Phase 2 → Phases 3, 4, 5 → Phase 6.
- US1 needs only Phase 2. US2 needs Phase 2 (and reuses the tokens from US1 for visual checks, but is testable on its own). US3 follows US1/US2 because it audits their result.
- Within US2: T009 → T010 → T011 → T012/T013 → T015; T014 is parallel; T016 after T013.
- `[P]` tasks (T009, T014) touch different files from their neighbours.

## Implementation strategy

MVP is Phase 2 + US1 (a dark OS gets a dark dashboard). Then US2 gives the override the user asked for, then US3 hardens it. Commit at the end of each phase.
